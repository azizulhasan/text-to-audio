# AtlasVoice — Free ↔ Pro Contract

> **Contract 1 of 4.** AtlasAiDev ships four free+Pro products; each has its own free↔Pro boundary
> and therefore its own contract in this folder:
> `atlasvoice-contract.md` (this) · `ar-contract.md` · `smart-local-ai-contract.md` · `atlasai-connector-contract.md`.
> A contract is **per-product** — the keys/filters below are AtlasVoice-specific (`tta_*` / `tts_*`) and do
> NOT apply to the other plugins.

> **Status: DRAFT — not adopted yet.** Review and revise before treating any of this as a rule.
> Purpose: make the AtlasVoice free↔Pro coupling explicit so a change in one plugin doesn't silently break the other.
> Treat every item below as a **public API**. Changing it = a breaking change → note it in BOTH plugins' changelogs.

## 1. How to use this document

Before editing any shared class or key, ask one question:
**"Does the Pro plugin read, write, or override this?"**
If yes → open Pro and grep for the key/filter/method **before** you edit the free plugin.

Shared classes most likely to affect Pro: `TTA_Helper`, `helpers.php`, `TTA_Api_Routes`, `AtlasVoice_Analytics`, anything in `includes/atlasvoice/`.

## 4. The filter bridge (`tts_*` / `tta_*` / `atlasvoice_*`)

Free `apply_filters(...)`; Pro `add_filter(...)`. These are the seams Pro plugs into. **Do not rename or change argument order/count without checking Pro.**

Highest-risk (Pro overrides these to enable premium behavior):
- `tts_get_player_id`, `tts_is_pro_active`, `tts_is_atlasvoice_addon_functional`
- `tts_reduce_enqueue`, `tts_button_inline_handles`
- `atlasvoice_player_content`, `atlasvoice__text_before_content`, `atlasvoice__text_after_content`
- `tts_post_has_mp3`, `tts_pro_plugins_data`
- `tts_emit_legacy_wrapper`, `tts_free_emit_atlasvoice_markers`
- `tta_should_load_button` (gates whether the player renders at all)

Content/cleaning seam: `tta_before_clean_content`, `tta_after_clean_content`, `tta_clean_content`, `atlasvoice_after_clean_content`.

---

## 5. Rules when changing a shared surface

1. Grep the **Pro** repo for the key/filter/method name first.
2. Prefer adding a new filter over changing an existing signature.
3. If shape must change, bump/note it in **both** changelogs and version-gate if needed.
4. Off/default path must preserve old behavior (e.g. highlight gated on `tta_highlight_settings`).
5. When in doubt, the boundary is an API — treat breakage as you would breaking a public function.
